Файл обновляется по мере того, как мы подключаем/меняем инструменты — не редактируйте вручную без необходимости, попросите меня обновить.

Контекст о магазине (позиционирование, ЦА, дифференциация, USP-словарь) для новых скиллов ниже собран в [`.agents/product-marketing.md`](.agents/product-marketing.md) — при необходимости попросите меня его обновить (`/mk-product-marketing`).

## 4. Маркетинг-портал — что уже есть и что можно улучшить

### Как устроен сейчас (`marketing-portal/`, Node/Express + SQLite, деплой в Docker на VPS)
- **Таблицы**: `drafts` (посты по источникам: новинки/акции/уценка/блог/пятничный/конкуренты — статусы `new/posted/dismissed`), `topics` (темы блога — `pending/approved/rejected/generated`), `plan_items` (маркетинг-план/календарь — `planned/in_progress/done/cancelled`), `promo_ideas` и `repost_suggestions` (аналогично `pending/approved/rejected`), `tasks`.
- **8 облачных Claude-рутин** (расписание в `dashboardRouter` → `ROUTINES`), которые пишут в эти таблицы через `marketing-portal/src/routes/api.js`, а вы одобряете/отклоняете результат в UI (`dashboardRouter` → `/topics/:id/status`, `/promo-ideas/:id/status`, `/repost-suggestions/:id/status`).
- Время везде хранится в UTC, отображается в МСК (`utcSqlToMskDisplay`).

### Куда встроить новые скиллы
- **Темы блога** (`topics`) — сейчас рутина явно только предлагает темы; отдать `mk-content-strategy` роль «проверь, что тема закрывает топик-кластер и не дублирует уже опубликованное» перед тем, как она попадает в очередь на одобрение.
- **Идеи акций** (`promo_ideas`) — прогонять через `mk-offers` (структура: механика + гарантия/срочность + формулировка) и `mk-marketing-psychology` (почему сработает) до показа вам — сейчас `rationale`-поле, судя по схеме, заполняется без явного фреймворка.
- **Репост-предложения** (`repost_suggestions`) — `mk-social` даёт критерии «что стоит репостить» (не просто «конкурент написал», а виральный потенциал/релевантность).
- **Маркетинг-план/календарь** (`plan_items`, типы `promo/campaign/news_hook/event`) — это по сути ручной аналог `mk-marketing-plan`. Можно раз в квартал прогонять текущий план через этот скилл как аудит: не пропущены ли сезонные активности, соответствует ли распределение AARRR-стадиям.
- **Мониторинг конкурентов** (рутина «Мониторинг конкурентов», источник `competitor` в `drafts`) — усилить через `mk-competitor-profiling`, чтобы черновики не просто фиксировали факт активности конкурента, а сразу давали структурированный вывод «что это значит для нас».

Это точечные усиления промптов **внутри самих облачных рутин** — я не вижу и не могу редактировать эти 8 рутин из текущей сессии (они управляются через claude.ai/code/routines, а не через `CronList` этого проекта — проверил, в этой сессии `CronList` пуст). Если хотите, чтобы я переписал промпты рутин с учётом `mk-*`-скиллов — пришлите мне текст текущего промпта каждой рутины (или откройте мне доступ к ним), и я перепишу.

### Обучение на одобренных/отклонённых материалах
Да, механизм для этого в портале уже есть на уровне данных — каждая таблица хранит статус решения. Но два уточнения:

1. **Я не могу «дообучить себя»** в буквальном смысле (файнтюнинг модели) — а вот выстроить **цикл обратной связи через промпты** могу: периодически смотреть на то, что вы одобрили/отклонили, находить закономерность («отклоняются идеи акций без сформулированной срочности», «одобряются темы блога с гео-привязкой к Крыму») и фиксировать это как явное правило в промпте рутины или в справочном файле, который рутина читает перед генерацией.
2. **Технически я сейчас не вижу живую базу** — `portal.db` лежит в Docker-volume на VPS (`marketing-portal/data/`, в `.gitignore`, не реплицируется в этот репозиторий), а прямого SSH-доступа к серверу у меня по вашему решению нет (см. проект «Server Monitoring» — ассистент без прямого SSH). Три варианта, как это обойти:
   - **Проще всего**: раз в 1-2 недели вы просите меня «проанализируй одобрения» и вставляете сюда экспорт (например, `sqlite3 portal.db "SELECT status, category, title FROM promo_ideas"` с сервера) — я анализирую и обновляю рекомендации.
   - **Автоматизировать через портал**: добавить в `marketing-portal` небольшой авторизованный `/api/stats`-эндпоинт с агрегацией по категориям/причинам отклонения (в `db.js` уже есть похожие функции — `getDraftStatsBySource`, `getTopicStats`, не хватает только версии для `promo_ideas`/`repost_suggestions` и разбивки по category), который я смогу дергать через `WebFetch`, если портал доступен по HTTPS с авторизацией.
   - **Дать точечный SSH/доступ к БД** только для чтения — тогда цикл можно сделать регулярным (например, через `/loop`).

   Готов сделать любой из вариантов 2 или 3 — какой предпочитаете?
