## [v2] Нейроответы — стратегия

### Когда коммерческая страница попадает в нейроответ

AI-поисковики (Яндекс Нейро, Google AI Overviews, ChatGPT Search) генерируют ответы **преимущественно на информационные запросы**.

| Тип запроса | Шанс нейроответа | Примеры |
|---|---|---|
| Транзакционный | Очень низкий | «купить смартфон Xiaomi Крым», «цена Redmi Note» |
| Коммерческий с условием | Низкий | «гарантия на Xiaomi в GOODMi», «трейд-ин смартфон Севастополь» |
| Сравнительный / выборочный | **Средний** | «чем Xiaomi 15 отличается от Redmi Note», «какой смартфон Xiaomi лучше» |
| Информационный про продукт | **Высокий** | «как выбрать планшет Xiaomi», «что важно в смартфоне до 30000» |
| Информационный про магазин | **Высокий** | «какая гарантия на технику Xiaomi», «как работает трейд-ин» |

**Коммерческие страницы GOODMi цитируются в нейроответах через:**
1. **FAQ-блок** — прямые ответы на информационные вопросы покупателей
2. **`.gm-intro-text`** — самодостаточные абзацы с конкретными фактами
3. **`WebPage.description`** в JSON-LD — первый источник для Яндекс Нейро и ChatGPT Search
4. **Блог-статьи** — основной канал для информационных запросов (вне scope этого скилла)

**Практическое правило:** оптимизация мета-тегов влияет на нейроответы косвенно (через `WebPage.description`). Основная работа по нейроответам — в контенте страницы (shop-page-builder-v2).

### Флаг нейроответа

Если пользователь явно упоминает нейроответы, AI Overviews, Яндекс Нейро или хочет «цитироваться» — активировать **информационный маршрут** в Step 1 и Step 2d.

## Приоритет трафика: Яндекс первый

Данные аналитики GOODMi:
- **Яндекс**: 58% органического трафика, конверсия в заказы в **2 раза выше**, чем с Google
- **Google**: 41% органического трафика
- **Расчётный вес выручки**: Яндекс ≈ **74%**, Google ≈ **26%**

**Принцип:** оптимизируем под Яндекс в первую очередь, обеспечиваем соответствие Google во вторую. Главное — максимальный трафик и позиции, не нарушая технические требования поисковых систем.

**Формула эффективного веса (на основе доли выручки):**
```
Эффективный вес = (Яндекс-значимость × 0.74) + (Google-значимость × 0.26)
```

## Geo-стратегия GOODMi

| Уровень | Гео | Где использовать |
|---|---|---|
| Региональный | **Крым** | title (обязательный геотаргет), description, JSON-LD areaServed |
| Двойное гео | **Крым, Севастополь** | title категорийных страниц — рекомендованный паттерн |
| Главный город | **Севастополь** | title (второй гео-сигнал), description, H1 сервисных страниц |
| Города присутствия | **Симферополь, Ялта** | description (USP самовывоза) |

**Принцип:**

- **Категорийные страницы — двойное гео в title:** использовать `«в Севастополе, Крыму»` — **Севастополь всегда первым** (4 из 6 магазинов, основной гео-сигнал бренда), Крым вторым. Допустимая длина title — до **~70 симв.**: Яндекс (58% трафика) показывает ≤70 симв. полностью; Google может обрезать «| GOODMi» в хвосте — это некритично, бренд виден в URL. Структура: ключевые слова и гео — ближе к началу, «| GOODMi» — в конце под возможную обрезку.
- **Если title > 70 симв. с двойным гео:** оставить только «в Севастополе».
- **Никогда:** не использовать «в Симферополе» как второй гео в title — там только 1 магазин.
- **H1 категорий:** гео не указывается. **Исключение: сервисные страницы — гео в H1 обязательно.**

## [v2] Broad vs quoted — режимы соответствия фразы в Wordstat

Yandex Wordstat различает два режима соответствия фразы:

- **Broad** (фраза без операторов, как есть) — считает любой запрос, где встречаются эти слова, в любом порядке, с любыми доп. словами, в любой словоформе. Отражает спрос на **всю семью фраз** вокруг формулировки, не на неё саму.
- **Quoted** (фраза в кавычках, передаётся прямо в строке — `"redmi note"`) — только точный порядок слов, без посторонних слов между/вокруг. Отражает спрос **именно на эту формулировку**.

`wordstat_bulk` и `wordstat_regions` без кавычек в строке возвращают **broad**. Quoted получить тем же вызовом, обернув фразу в кавычки внутри `phrases`/`phrase`. **Проверено эмпирически на инструменте этого проекта** (regions 959+977): `redmi note` — broad 20666 (Севастополь 3949 + Крым 16717), quoted 29 (Севастополь 3 + Крым 26) — расхождение ~700×. Composite-запрос `xiaomi робот пылесос гарантия` — broad 10, quoted 0: то, что в broad выглядит как «небольшой, но реальный спрос», на деле формулировка, которую никто не ищет буквально. Расхождение непредсказуемо по величине и зависит от конкретной фразы — не полагаться на broad как на приближение quoted.

**Правило применения:**
- **Относительные сравнения** (кириллица vs латиница, формальный vs разговорный термин, выбор синонима для H1/title — весь гео-каскад Step 2b) — использовать **broad**: обе стороны сравнения измерены одинаково, соотношение не искажается, даже если абсолютные числа завышены.
- **Демонд-фильтр составных USP-фраз** («[товар/категория] + гарантия/доставка/трейд-ин/кредит/самовывоз» — решение, включать ли фразу в description/`WebPage.description`/семантическое ядро) — использовать только **quoted** (см. Step 3 «Демонд-фильтр USP» ниже). Broad для таких composite-фраз почти всегда даёт крошечные ненулевые числа, которые ничего не говорят о реальном спросе на точную формулировку.
- Если broad = 0 — quoted можно не проверять, гарантированно тоже 0 (экономия запросов).
- Собирать оба числа одним батчем `wordstat_bulk`, добавляя в список `phrases` и обычную, и `"кавычную"` форму каждой composite-фразы.

Методология портирована из проекта Maxmobiles (эмпирически перепроверена на этом проекте выше, не принята вслепую) — источник: `wordstat-pixelplus-methodology-handoff.md`.

## Workflow (execute in order)

### Step 1 — Parse the request

Extract from the user's message:
- **Page type**: конкретная модель / серия / топовая категория / аксессуары / сервис-услуга
  - **Исключение — пагинация / фильтры** (`?page=2`, `?features_hash=...`): скилл не генерирует мета-теги для этих URL. Решение — `canonical` на первую страницу категории или `noindex` на уровне CS-Cart настроек.
- **Product name / category** (e.g., Xiaomi 15 Pro, Redmi Note, планшеты, ремонт)
- **Keyword data**: если пользователь предоставил список ключей с частотностью/значимостью
- **Quantity**: single page or batch
- **[v2] Флаг нейроответа**: упомянуты ли нейроответы, AI Overviews, «цитируемость» — если да, активировать Step 2d
- **[v2] Мультибренд — обязательный блокирующий вопрос.** Для топ-категорий и аксессуаров (тип страницы неочевиден по бренду) — спросить **до** начала Step 2: «Ассортимент этой страницы — конкретный бренд (Xiaomi), или мультибренд/смешанный ассортимент?». Не спрашивать только если бренд однозначно ясен из самого названия страницы (конкретная модель типа «Xiaomi 15 Pro», серия «Redmi Note» — это всегда Xiaomi по определению). Ждать ответ = блок, не генерировать теги с молчаливым предположением о бренде.
  - Если **мультибренд** — активировать **Step 2e**, зафиксировать список вторичных брендов если названы. Xiaomi всегда основной бренд для SERP-запросов. Перед включением любого вторичного бренда в title/H1 — уточнить, есть ли товар этого бренда в каталоге (бренд не из каталога в title создаёт несоответствие ожиданий → рост отказов).
  - Если **мультибренд со сменным/неподтверждённым составом брендов** (пользователь не может назвать конкретные 1–2 вторичных бренда, ассортимент часто меняется) — **не фиксировать бренд в H1/title вообще** (ни Xiaomi, ни другие) — см. правило в Step 3 «Многобрендовые категории». Бренд остаётся только на уровне карточек товаров на странице, не в теге.

**Маршрут выполнения:**

```
keyword data НЕ предоставлена → Step 2 (3 запроса) → [Step 2e если мультибренд] → [Step 2d если флаг] → Step 2b → Step 2c → Step 3
keyword data предоставлена    → Step 2-mini (3 запроса) → [Step 2e если мультибренд] → [Step 2d если флаг] → Step 2b → Step 2c → Step 3
```

**Step 2c (Gap Analysis) выполняется всегда.** При пропущенном основном Step 2 — выполнить **Step 2-mini**: 2 WebSearch параллельно (обязательные):
1. `"купить [Категория/Модель] Крым"` — поиск реальных конкурентов
2. `"[Категория/Модель] Севастополь"` — региональные конкуренты

**Опциональный запрос №3** — только если планируется HTML-блок (shop-page-builder):
3. `"как выбрать [Категория/Модель] Xiaomi"` — FAQ-семена для shop-page-builder

После Step 2-mini — также выписать домены из топ-10 по каждому запросу и проверить наличие приоритетных конкурентов GOODMi (полный список — в Step 2). Найденных пометить **★** для Step 2c.

**Batch-режим — стратегия SERP-запросов:**
- **2–4 страницы**: запустить WebSearch для каждой страницы параллельно (N×3 одновременно).
- **5+ страниц**: группировать похожие категории. SERP по «купить Redmi Крым» переиспользовать для всех серий Redmi. Gap Analysis — один общий, если страницы из одной категории.

### Step 2 — SERP research

Выполнять когда: keyword data не предоставлена.

Кириллические варианты брендов для запроса №3 — см. таблицу в Step 2b.

Run **3 WebSearch queries in parallel** (обязательные):

1. `"купить [Категория/Модель] Севастополь"` — title-паттерны приоритетного города
2. `"купить [Категория/Модель] Крым"` — региональные паттерны конкурентов
3. `"[Кириллический вариант] купить крым"` — реальная частотность кириллики в региональной выдаче

**Опциональный запрос №4** — выполнять только если планируется HTML-блок (shop-page-builder):

4. `"как выбрать [Категория/Модель] Xiaomi"` — FAQ-семена: вопросы покупателей, критерии выбора

**После получения результатов — обязательно:**

По каждому запросу явно выписать домены из первых 10 результатов (только домен верхнего уровня: `wildberries.ru`, не `www.wildberries.ru`). Это основа для расчёта доминирования агрегаторов в Step 2b.

Если `goodmi.ru` присутствует в топ-10 — зафиксировать позицию и пометить запрос:
- Позиция 1–5 → **«укрепление»** — работаем над удержанием
- Позиция 6–10 → **«рост»** — приоритет для оптимизации title
- Не в топ-10 → **«новый»** — требует контентных усилий

```
aliexpress.ru · e-katalog.ru · price.ru · tmall.com · goods.ru
technopark.ru · regard.ru · pleer.ru
```

Агрегаторов невозможно обогнать — изучать их title бессмысленно.

**Приоритетный список конкурентов GOODMi (особенно важно для Google-выдачи):**

После выписки доменов из топ-10 — проверить, присутствует ли кто-то из известных конкурентов:

| Домен | Тип |
|---|---|
| mi-shop.com | монобренд Xiaomi, федеральный |
| mi-xx.ru | монобренд Xiaomi |
| ru-mi.com | монобренд Xiaomi |
| mi-life.ru | монобренд Xiaomi |
| gadjet-sevastopol.ru | региональный, Севастополь |
| gadjet-crimea.ru | региональный, Крым |

- Найден в топ-10 → пометить **★ обязательный анализ в Step 2c**
- Не в топ-10 или страница слабая (пустой контент, нет SEO) → пропустить
- Список приоритетный, не исключительный: другие реальные конкуренты из SERP тоже анализировать

**Анализировать только реальных конкурентов:**
- Специализированные магазины техники Xiaomi (монобренды)

- Онлайн-магазины без маркетплейс-механики

### [v2] Step 2e — Мультибренд SERP (обязателен при наличии вторичных брендов)

**Когда выполнять:** Step 1 зафиксировал 2+ бренда на странице. Выполнять параллельно со Step 2d (или сразу после Step 2, если Step 2d не активирован).

**Для каждого вторичного бренда** (не Xiaomi) — запустить **2 WebSearch параллельно**:

1. `"купить [Бренд] [категория] Севастополь"` — есть ли GOODMi в топ-10? Кто конкурирует?
2. `"[Бренд] официальный магазин Россия [категория]"` — есть ли у бренда свой интернет-магазин?

При 2 вторичных брендах (например Dreame + Roborock) — **4 запроса параллельно**.

**После получения результатов — для каждого бренда заполнить таблицу:**

```
## Мультибренд SERP: [Категория]

| Бренд | Офиц. магазин в топ-10 | Агрегаторов | GOODMi в топ-10 | Флаг |
|---|---|---|---|---|
| [Бренд] | да / нет → [домен] | N | да / нет | 🎯 / 👁 / — |
```

**Правила присвоения флага:**

| Условие | Флаг | Действие |
|---|---|---|
| Есть офиц. магазин бренда в топ-10 | **—** | Брендовый запрос нереалистичен. Бренд → только в description как ассортиментный сигнал. |
| Нет офиц. магазина + 0–1 агрегатор | **🎯** | GOODMi может конкурировать. Бренд → кандидат в title. |
| Нет офиц. магазина + 2–3 агрегатора | **👁** | Сложно, но мониторить. Бренд → description. |
| Нет офиц. магазина + 4+ агрегатора | **—** | Не включать в title. |

**Стратегические выводы Step 2e передать в Step 3:**
- Бренд с флагом **—** → упомянуть в description и H1 (как ассортиментный факт), **не включать в title**
- Бренд с флагом **🎯** → кандидат в title (Вариант с мультибрендом)
- Бренд с флагом **👁** → включить в description, в title опционально

### [v2] Step 2d — Информационный SERP (для нейроответов)

**Когда выполнять:** активирован флаг нейроответа из Step 1 ИЛИ пользователь планирует HTML-блок (тогда данные передаются в shop-page-builder-v2).

- Какие информационные вопросы присутствуют в поиске

- Какие вопросы не закрыты конкурентами → приоритет для FAQ-контента

```
- «[запрос]» — [кто цитируется / не закрыт]
- «[запрос]» — [кто цитируется / не закрыт]

### Рекомендации:
→ FAQ: включить вопрос «[вопрос из Step 2d]» — прямой кандидат в нейроответ
→ WebPage.description: начать с прямого ответа на «[запрос]»
→ Блог: тема «[расширенный информационный запрос]» — вне scope мета-тегов
```

### Step 2b — Анализ ключевых слов (Wordstat-кластерный анализ — приоритетный метод)

**Принцип: частотность (измеренная, региональная) важнее входного запроса пользователя, привычной терминологии сайта и SERP-паттернов конкурентов.** Никогда не использовать сид-термин (название страницы/категории из Step 1) как есть — строить кластер синонимов и проверять частоту каждого варианта. Если топ-1 кластера — не то слово, которое обычно используется на сайте, побеждают данные, а не привычка.

**1. Построение кластера кандидатов.** Варьировать для сид-термина:
- тип-слово: формальный синоним («внешний аккумулятор», «портативный аккумулятор») и разговорный («повербанк»)
- написание единицы измерения: латиница («mAh»), кириллица («мач»), и вариант вообще без единицы — часто оказывается самым частотным
- предлог: «на N» / «N» без предлога

**2. Проверка частоты по гео-каскаду** (см. таблицу выше «Wordstat-регионы»): для каждого кандидата — `wordstat_regions` с regions=[959,146,977] + `wordstat_top` для национального totalCount и LSI/associations.

**3. Взвешенный балл кандидата:**
```
Балл = (доля_Севастополь × 0.55) + (доля_Симферополь × 0.20) + (доля_Крым × 0.15) + (доля_Россия × 0.10)

доля = count кандидата на уровне ÷ сумма count всех кандидатов кластера на этом же уровне
```
Считать именно **долю**, не сырые числа — иначе Россия всегда побеждает за счёт масштаба населения независимо от весов.

**[v2] Здесь используется broad-частота** (фразы без кавычек) — это относительное сравнение вариантов кластера между собой, обе стороны меряются одинаково (см. «Broad vs quoted» выше), искажение от завышенных абсолютных чисел не влияет на итоговое ранжирование. Не путать со следующим шагом демонд-фильтра USP (Step 3) — там обязателен **quoted**.

**4. Распределение по тегам:**
- **Топ-1 по взвешенному баллу → title.**
- **LSI/associations топ-1** (из `wordstat_top` по фразе-победителю) **→ H1.** H1 обязан использовать другую лексическую ветку кластера (например формальный синоним вместо разговорного термина title), а не тот же головной термин, переставленный местами — иначе H1/title/description начинают дублировать друг друга.
- Остаток кластера (не top-1, не выбранный для H1) → хвост description, только после демонд-фильтра (Step 3).
- Термины с частотой **< 10 по Крыму (977)** — исключаются из title/H1/description полностью, не понижаются в приоритете.

**5. Разделение по интенту (обязательно перед вставкой в тег).** Информационные LSI-фразы (вопросы «можно ли», «на сколько хватает», «отзывы», сравнения, сезонность) — **не вставляются в мета-теги**, даже при высокой частоте: коммерческий тег и информационный интент не смешиваются в одном предложении. Фиксировать их отдельно как FAQ-семена для Step 2c/Step 2d.

**Fallback — если Wordstat недоступен или нерелевантен для типа страницы** (например узкая сервисная услуга без стабильного поискового спроса): использовать SERP-эвристику ниже.

**Когда Wordstat недоступен и keyword data не предоставлена — оценка значимости по SERP (fallback):**

Если численные данные ключей отсутствуют (SERP-маршрут), оценить значимость по частоте появления ключа в title/H1 реальных конкурентов (не агрегаторов) из Step 2:

| Частота в топ-10 реальных конкурентов | Оценочная значимость |
|---|---|
| 3+ упоминаний | ~50 — кандидат в title |
| 1–2 упоминания | ~20 — кандидат в description |
| 0 упоминаний | < 15 — пропустить |

Пометить в комментарии: «значимость оценена по SERP-частоте, не по keyword data».

**Fallback при малом числе реальных конкурентов (1–2 в топ-10):**
Если реальных конкурентов ≤ 2, порог 3+ не применять. Ключ, присутствующий в title хотя бы одного реального конкурента, считать кандидатом в title (~40). Пометить: «мало реальных конкурентов — оценка по присутствию в title».

**Когда keyword data предоставлена внешним источником (не Wordstat-кластером выше) — расчёт эффективного веса:**

> Эта формула — про источник данных (Яндекс vs Google), другая ось, чем гео-каскад Step 2b (Севастополь/Симферополь/Крым/Россия). Если пользователь принёс готовые цифры значимости без региональной Wordstat-проверки — использовать её как fallback.

```
Эффективный вес = (Яндекс-значимость × 0.74) + (Google-значимость × 0.26)
```

Если источник не разделён по системам — использовать значимость как есть.

**Классификация ключей по порогу:**

| Значимость | Решение |
|---|---|
| ≥ 35 | **Кандидат в title** — точное вхождение даёт реальный прирост трафика Яндекса |
| 15–34 | **Кандидат в description** — семантический хвост |
| < 15 | Пропустить — не окупает место в теге |

Если максимальный эффективный вес в keyword data < 35 — порог не применять. Использовать ключ с наибольшим весом как основу title, пометить в комментарии: «ключи ниже порога 35, выбран наиболее весомый». Нишевые категории часто имеют низкочастотную семантику — это не ошибка.

**[v2] Официальный магазин бренда — блокер для национальных запросов (проверять до подсчёта агрегаторов):**

**Важное исключение — региональные запросы:** официальные магазины брендов, как правило, **не geo-таргетированы** и не попадают в топ-10 по запросам с гео (Севастополь, Крым). ### Step 2c — Gap Analysis реальных конкурентов

Выполнять **всегда** (на обоих путях). Двухшаговый процесс: сначала из SERP-сниппетов, затем при необходимости WebFetch.

**Шаг 1 — быстрый анализ SERP-сниппетов (без дополнительных запросов):**
Для каждого реального конкурента из топ-10 извлечь прямо из результатов поиска:
- Title (виден в SERP напрямую)
- Наличие meta description: если сниппет содержит текст — есть; если пусто или показан только URL — отсутствует
- Кириллика в title/сниппете (да/нет)

**Шаг 2 — WebFetch: условно, максимум 2 параллельных запроса:**
Запускать только если в топ-10 найден ★-конкурент. Тогда параллельно:

- **1 WebFetch на URL категории GOODMi** — для извлечения актуального ассортимента моделей в description

Если ★-конкурентов нет → 1 WebFetch на следующего реального конкурента из SERP. WebFetch на GOODMi — только при наличии ★-конкурента.

**Приоритет выбора конкурента для WebFetch:**
1. ★-конкурент из приоритетного списка (Step 2), найденный в топ-10
2. Следующий реальный конкурент из SERP (не агрегатор)
3. Если ни одного реального — fallback с агрегатором (см. ниже)

**Fallback при сбое WebFetch:**
Если WebFetch вернул менее 200 символов читаемого текстового контента (заголовки, параграфы, перечни USP — без учёта HTML-тегов и скриптов) — пропустить этого конкурента, перейти к следующему из SERP. 1. Взять страницу наиболее релевантного агрегатора → зафиксировать пробелы (нет локального сигнала, нет FAQ, нет трейд-ина, нет кириллики)

### Step 2f — URL Analysis

**Когда выполнять:** всегда, когда пользователь предоставил URL страницы.

**Цель:** проверить, соответствует ли URL-слаг главному ключевому кластеру страницы, и предложить смену при несоответствии.

**Алгоритм:**

1. Извлечь слаг из URL (часть между доменом и trailing slash): `dlya-doma`, `roboty-pylesosy` и т.д.
2. Определить головной ключ кластера из Step 2b (ключ с наибольшим эффективным весом).
3. Оценить степень покрытия:
   - **Полное** — все значимые слова головного ключа присутствуют в слаге → URL оптимален, не менять.
   - **Частичное** — часть слов головного ключа отсутствует → оценить пользу замены.
   - **Нет покрытия** — слаг технический или не связан с ключом → рекомендовать замену.
4. Проверить URL ★-конкурентов из SERP (Step 2): используют ли они ключевые слова в слаге?
5. Свериться с паттерном URL GOODMi (CLAUDE.md, раздел «Canonical URL patterns»):
   - Бренд «xiaomi» в слаге: добавлять только если в существующем паттерне есть прецедент (`televizory-xiaomi`, `monitory-xiaomi`). Для основных категорий (`smartfony`, `planshety`) — без бренда.
   - Длина слага: не более 4 слов.

**Формат вывода:**

```
## URL Analysis: [текущий URL]

Слаг: [slug]
Головной ключ: [ключ, вес]
Покрытие: полное / частичное / нет
Конкуренты: [домен] использует [slug] — [совпадает / нет]

→ Рекомендация: оставить / заменить на [новый-slug]
→ Причина: [одна фраза]
```

Если рекомендована смена — вывести итоговый URL явно: `https://goodmi.ru/[новый-slug]/`

### Step 3 — Генерация мета-тегов

> **Правило старшинства:** при противоречии между структурным шаблоном/примером (в т.ч. Step 3a) и именованным правилом (Демонд-фильтр USP, антиспам-правило синонимов и т.п.) — побеждает именованное правило. Примеры иллюстрируют формат, не отменяют фильтры.

**Цель не шаблон, а покрытие.** Максимально охватить высоковесовые ключи в рамках технических ограничений поисковых систем.

#### Правила по типу страницы

| Тип страницы | H1 — формат | Гео в H1 | «Купить» в title | Трейд-ин — кандидат в USP? |
|---|---|---|---|---|
| Топовая категория | `[Тип товара] Xiaomi` | Нет | Внутри title | Да, если пройдёт демонд-фильтр |
| Серия моделей | `[Тип товара] [Серия]` | Нет | Внутри title | Да, если пройдёт демонд-фильтр |
| Конкретная модель | `[Тип товара] [Полное название модели]` | Нет | Первое слово в title | Да, если пройдёт демонд-фильтр |
| Аксессуары | `[Тип аксессуара] Xiaomi` | Нет | Внутри title | Нет — исключается по типу страницы, не по фильтру |
| Сервис / услуга | `[Услуга] Xiaomi в [Город]` | **Да — обязательно** | Не использовать | Нет |

> Эта колонка задаёт только *допустимость* трейд-ина/кредита/доставки для типа страницы (кандидат ли он в принципе) — не факт включения. Факт включения в description решает исключительно «Демонд-фильтр USP» (Step 3) и его обязательная таблица в Step 4: без подтверждения в Step 2b LSI разрешена только одна фраза-исключение («гарантия 1 год»).

**Специфика USP по типу:**
- **Аксессуары**: трейд-ин и кредит недопустимы по типу страницы (не только по фильтру); из допустимых — гарантия, совместимость, доставка — через демонд-фильтр
- **Сервис**: гарантия на работы, оригинальные запчасти, срок ремонта, несколько точек в городе — это конкретные факты услуги, не шаблонные магазинные USP, демонд-фильтру не подлежат

#### H1 — что делает заголовок сильным

H1 — навигационный заголовок. Пользователь уже на сайте, коммерческие сигналы ему не нужны. Весь коммерческий сигнал — в title и description.

**Правила длины и формата:**
- Диапазон: **15–45 симв.** (проверять явно)
- Если название продукта < 15 симв. — добавить тип устройства перед ним: «Смартфон POCO X7» (18 симв.)
- Запрещено: «Купить», «официальный», «авторизованный»

**[v2] Число в H1 — всегда множественное:**

Wordstat не различает единственное/множественное число (лемматизирует запрос — частота идентична для обеих форм), поэтому выбор числа не может опираться на частотные данные. Все страницы, для которых применяется этот скилл, — листинги/категории с карточками нескольких товаров; страницы одного конкретного SKU здесь не генерируются никогда. Поэтому тип-слово в H1 (и связанный с ним тип-термин в title/description) — **всегда множественное число**, включая страницы конкретной модели.

**Позитивные правила — что делает H1 сильным:**

1. **Порядок слов**: тип устройства → бренд → серия/модель
   - ✅ «Смартфоны Xiaomi» — тип первым, бренд вторым
   - ❌ «Xiaomi смартфоны» — обратный порядок хуже читается

2. **Полное официальное название** — не сокращать, не переводить на кириллицу:
   - ✅ «Смартфоны Redmi Note 15 Pro Plus»
   - ❌ «Смартфон Редми Нот 15» — единственное число и кириллица в H1 не нужны

3. **Для серий** — тип + серия, не только серия:
   - ✅ «Смартфоны Redmi Note»
   - ❌ «Redmi Note» — без типа устройства теряет навигационный смысл

4. **Для мультибрендовых категорий** — основной бренд первым:
   - ✅ «Наушники Xiaomi, Marshall»
   - ❌ «Marshall и Xiaomi наушники»

5. **Для сервисных страниц** — услуга + бренд + город:
   - ✅ «Ремонт Xiaomi в Севастополе»
   - ❌ «Ремонт телефонов» — слишком широко, без бренда и города

#### title — варианты по разным стратегическим осям

**Стратегия длины title — приоритет ключей, не лимит:**

Поисковики индексируют полный title целиком вне зависимости от визуального обрезания в SERP. Не жертвовать ключами ради длины — важные слова в начале, «| GOODMi» в конце допускается к обрезанию.

- **Яндекс** (~70 симв. показывает полностью) — основной приоритет (58% трафика)
- **Google** (~65 симв. / 580px) — ключи в начале; обрезание «| GOODMi» некритично, бренд виден в URL
- **Ориентир:** 70–80 симв. При превышении 80 — сокращать. Жёсткого лимита нет.

**Порядок приоритетов в title (от начала к концу):**
1. Продукт/категория + Xiaomi
2. Коммерческий сигнал («купить», «магазин», «цены»)
3. Гео — Севастополь первым, затем Крым
4. «| GOODMi» — всегда последним; допускается к обрезанию

**Пользователь может давать рекомендации по словам для title** в ходе работы — принять их как приоритетные ключи и вписать, соблюдая порядок выше.

**Ограничения (неизменны):**
- Нет keyword stuffing, нет caps, нет `!`, нет цен в ₽
- `GOODMi` всегда последним после `|`

**Три стратегические оси для вариантов — варианты должны различаться по оси, а не только по кириллике:**

| Ось | Что варьировать | Пример |
|---|---|---|
| **А — кириллика** | с/без кириллического варианта бренда | «Xiaomi» vs «Xiaomi (Сяоми)» |
| **Б — коммерческий сигнал** | «купить» vs «цена» vs «гарантия» | «купить в Крыму» vs «цена и гарантия» |
| **В — длина/гео** | одно гео «в Севастополе» vs двойное «в Севастополе, Крыму» (+7 симв.); порог ~70 симв. — граница выбора двойного/одиночного гео, не общий лимит title (общее правило длины — см. Step 3, «Стратегия длины title»); обрезка «\| GOODMi» в Google некритична | Двойное гео «в Севастополе, Крыму» — по умолчанию при длине ≤ ~70 симв.; одно «в Севастополе» — только если не вписывается |

**Процесс генерации title:**

1. Взять ключ с максимальным эффективным весом → основа title
2. Построить **2–3 варианта** по разным осям (не только ось А)
3. Для каждого посчитать покрытие ключей и длину
4. Учесть правило первого слова (см. ниже)

**Если title > 80 симв. — порядок усечения:**
1. Убрать кириллику в скобках (если есть) — экономит 8–15 симв.
2. Убрать второй гео: «в Севастополе, Крыму» → «в Севастополе» — экономит 7 симв.
3. Убрать наименее значимый коммерческий сигнал (оставить тот, что ближе к ТОП-запросу)
4. Крайний случай: оставить только продукт + главный гео + GOODMi

**Правило первого слова в title:**
- Категории и серии: продукт первым (`Redmi Note — купить в Крыму...`)
- Конкретная модель: «Купить» первым (`Купить Xiaomi 15 Pro...`)
- Сервис: услуга первой (`Ремонт Xiaomi в Севастополе...`)

**Вывод вариантов — показывать пользователю все варианты, не выбирать самостоятельно:**

```
Вариант А: «[title]» ([N] симв.) — [ось: кириллика / коммерч. сигнал / длина]
→ Покрывает: [что именно]. Сильно для: [Яндекс / Google / оба].

Вариант Б: «[title]» ([N] симв.) — [ось]
→ Покрывает: [что именно]. Сильно для: [Яндекс / Google / оба].

Вариант В: «[title]» ([N] симв.) — [ось] (если есть)
→ Покрывает: [что именно].

→ Рекомендация: Вариант [X] — [одна фраза, обоснование из Step 2b данных].
```

**[v2] Главный принцип композиции (H1/title/description):** содержимое гибких слотов — хвост title сверх топ-1-ключа и слот характеристик/LSI в description — собирается напрямую из таблицы ключей+LSI Step 2b/2c, а не сочиняется по шаблону. Порядок внутри гибкого слота — по убыванию взвешенного балла Step 2b, самое значимое ближе к началу слота (keyword prominence: чем раньше термин, тем больше веса ему достаётся и у поисковика, и у нейроответа, и у читателя). Роль-ориентированные слоты (гео-сигнал, USP-якорь, CTA, E-E-A-T) в эту сортировку не входят — их позицию фиксирует AEO-паттерн независимо от частоты. Демонд-фильтр и антиспам-правило синонимов определяют, что вообще допустимо включать, — вес решает только порядок среди уже допущенного (правило старшинства из начала Step 3 действует и здесь). Не жертвовать читаемостью ради охвата — но и не оставлять бюджет неиспользованным, если в таблице Step 2b остались провалидированные фразы; исключение: демонд-фильтр всё равно сильнее — свободное место не повод добавить вторую неподтверждённую магазинную USP-фразу сверх одной разрешённой.

Пример сортировки внутри гибкого слота: если «Xiaomi (Сяоми)» (644 показа) и «портативный аккумулятор» (9 показов) оба ещё не использованы — первым идёт «Сяоми».

**[v2] Категорийное усиление (отдельный от Step 2b-кластера механизм):** для страниц модели/серии — проверить родительский категорийный термин (например «смартфоны Redmi» для страницы Redmi A7 Pro) тем же гео-каскадом Wordstat. Если региональный спрос подтверждён — добавить **одно** упоминание в гибкий слот description, после кластерных характеристик, перед E-E-A-T. Это отдельная, более широкая сущность, а не переформулировка головного термина H1/title — не нарушает проверку Step 4 «H1/title/description — разные ветки кластера».

**[v2] Диапазон вместо единичного значения:** любая числовая характеристика (мощность быстрой зарядки, ёмкость и т.п.), которая варьируется между моделями на странице-листинге — даётся диапазоном («от 22.5 до 67 Вт»), не единичным значением. Единичное число на листинге с разными моделями вводит в заблуждение по ассортименту.

#### meta description

**Технические ограничения:**
- Google Desktop: ~155 симв. видимый сниппет
- Яндекс расширенный сниппет: до 300+ симв.
- **CS-Cart жёсткий лимит: 255 символов** — всё сверх обрезается при сохранении
- Оптимальная длина: **180–250 симв.** (5 симв. запас до лимита CS-Cart)

**AEO-паттерн первого предложения (Featured Snippet и AI Overviews):**

Структура: `[Продукт/Категория] в GOODMi — [прямой ответ на коммерческий запрос]`

AI-системы цитируют предложения, которые:
- Начинаются с объекта запроса (не с «Мы», не с «GOODMi»)
- Содержат прямой ответ в первых 10 словах
- Включают гео-сигнал (Крым / Севастополь)
- Заканчиваются конкретным фактом, а не только призывом
- **[v2] Содержат минимум одно конкретное число** («6 точек», «с 2016 года», «365 дней»)

❌ Слабо: «GOODMi предлагает смартфоны Xiaomi с доставкой по России.»
✅ Сильно: «Смартфоны Xiaomi в Севастополе, Крыму – гарантия 1 год, модели в наличии.»

**Структура description — фиксированный порядок:**

*Для товарных страниц (категория / серия / модель / аксессуары):*
```
[AEO-первое предложение: продукт + гео-сигнал + USP-якорь (состав определяет «Демонд-фильтр USP» ниже — не 3 USP по умолчанию) + CTA]     ← до ~155 симв.
[Характеристики/LSI из Step 2b — по убыванию взвешенного балла, не как попало]      ← приоритет в хвосте
[Категорийное усиление — родительский термин, если подтверждён спросом отдельно]    ← после характеристик
[Кириллические хвосты — если значимость 15–34, ещё не использованы выше]           ← после категорийного усиления
[E-E-A-T: Experience («с 2016 года») → Authoritativeness]           ← в конце хвоста
```

*Для сервисных страниц (ремонт, VPN, трейд-ин):*
```
[AEO-первое предложение: услуга + город + главный USP сервиса]      ← до ~155 симв.
[Перечень работ / услуг: что конкретно делается]                   ← приоритет в хвосте
[Условия сервиса: запчасти, срок, запись]                          ← после перечня работ
[E-E-A-T: опыт мастеров, количество точек]                         ← в конце хвоста
```

Порядок фиксирован: AI-системы цитируют начало хвоста чаще конца.

- Ключи, не попавшие в title → интегрировать в description естественно
- Доставку и самовывоз указывать вместе, но только если прошли демонд-фильтр: «доставка СДЭК, самовывоз в Крыму»
- CTA до 155 симв.: «Заказывайте онлайн» / «Оформите заказ» / «Выбирайте в каталоге»
- Gap-USP из Step 2c: то, чего не упомянули конкуренты — выдвинуть вперёд

**E-E-A-T в description — приоритет при нехватке места:**

| Приоритет | Сигнал | Фраза | Условие |
|---|---|---|---|
| 1 — обязательно (с учётом демонд-фильтра) | Trustworthiness | «гарантия 1 год» — разрешённое исключение, всегда доступна; «трейд-ин», «доставка СДЭК» — только если подтверждены в Step 2b LSI | Гарантия — всегда в первых 155 симв.; остальные — только при подтверждении спроса |
| 2 — обязательно | Expertise | «фирменный магазин техники Xiaomi» | Всегда, первые 155 или сразу после |
| 3 — при длине > 180 | Experience | «с 2016 года» / «более 9 лет» | В хвосте, если влезает |
| 4 — при длине > 220 | Authoritativeness | «крупнейший магазин Xiaomi в Крыму» | Только если есть место |

При нехватке места жертвовать 3 и 4, но не 1 и 2.

**Approved USPs:**
- «гарантия 1 год»
- «доставка СДЭК» / «доставка по России через СДЭК»
- «самовывоз в Крыму» / «самовывоз в Севастополе, Симферополе, Ялте» / «6 точек в Крыму»
- «трейд-ин»
- «кредит» / «покупка в кредит»
- «фирменный магазин техники Xiaomi»
- «с 2016 года» / «более 9 лет»
- «бонусная программа GOODMi»

⚠️ Этот список — разрешённый словарь фраз, не чек-лист «вставить всё». Какие из них реально попадут в description конкретной страницы — решает «Демонд-фильтр USP» ниже, не порядок в списке.

> Запрещено везде: «рассрочка», «официальный», «авторизованный», эмодзи, цены в ₽, `!`

**[v2] Демонд-фильтр USP:**

Перед вставкой в description любой типовой магазинной фразы («доставка СДЭК», «самовывоз в N точках» и т.п.) — проверить её частоту как composite-запрос «[головной термин страницы] + USP» **в quoted-режиме** через `wordstat_bulk(phrases=["\"[термин] [USP-фраза]\""], regions=[959,146,977])` (см. «Broad vs quoted» выше). **Не путать с присутствием в broad-кластере/LSI Step 2b** — broad для составных USP-фраз почти всегда даёт ложноположительные крошечные ненулевые числа (проверено эмпирически: `xiaomi робот пылесос гарантия` broad=10, quoted=0). Quoted-частота ~0 по всем формулировкам → не вставлять: эта информация уже есть на страницах Доставка/Контакты/Оплата и в тексте самого HTML-блока страницы — повторение в description не увеличивает охват, только тратит символьный бюджет. Освободившееся место — под LSI-фразы кластера (реальные атрибуты товара: характеристики, кириллические варианты, синонимы), которые расширяют охват по формулировкам запроса.

Исключение: разрешена **одна** фраза-якорь доверия (например «гарантия 1 год») даже без частотного подтверждения — не более одной, конверсия важнее чистого охвата для одной короткой фразы.

**[v2] Антиспам-правило синонимов:**

Если в одном теге используется несколько ветвей кластера (разговорный термин + формальный синоним, или бренд латиницей + кириллицей) — способ объединения зависит от длины фразы:

- **Однословная калька бренда** («Xiaomi/Сяоми») — скобка при первом упоминании допустима: «Xiaomi (Сяоми)». Естественной альтернативы для одного слова почти нет.
- **Многословное название модели/серии** («Redmi A7 Pro/Редми А7 Про», «Redmi Note/Редми Нот») — скобка сразу после оригинала читается как словарная калька, а не как текст. Вместо этого — естественное упоминание кириллического варианта в отдельном предложении с другой синтаксической ролью (чаще всего удобно в CTA: «Оформляйте заказ на Редми А7 Про онлайн»), не рядом с первым упоминанием латиницей.

В обоих случаях — каждое ключевое понятие называется в description один раз, не повторяется голова фразы отдельными предложениями подряд: иначе текст читается как список ключевых слов, а не как текст.

**Многобрендовые категории:**
- Если 1–2 вторичных бренда подтверждены и стабильны в каталоге: H1: `[Тип товара] Xiaomi, [Бренд2]` — не более 2 брендов; title: `[Тип товара] [Бренды] — купить в Крыму | GOODMi`; остальные бренды → description.
- **[v2] Если ассортимент смешанный/меняющийся и 1–2 конкретных бренда назвать нельзя** (см. блокер Step 1): бренд **не фиксируется** ни в H1, ни в title — только `[Тип товара] [Спецификация] — купить в Крыму | GOODMi`, без названия бренда вообще. Освободившееся место в description — под характеристики товара (диапазоны, features), не под бренд. Соответствует принципу «для смешанного ассортимента карточки/бренд-теги не жёстко фиксируются».

#### [v2] JSON-LD description — строгие правила для нейроответов

**`WebPage.description`** — главный источник для Яндекс Нейро и ChatGPT Search.

При использовании совместно с shop-page-builder:
- Должен содержать **полное первое предложение** meta description (не обрезать на 155 симв. — предложение должно быть завершённым). Именно его используют Яндекс Нейро и ChatGPT Search для генерации ответов.
- **[v2] НЕ начинать** с «GOODMi», «Мы», «В нашем магазине» — начинать с объекта запроса
- **[v2] Должен содержать минимум одно конкретное число**: «6 точек», «с 2016 года», «365 дней», «1 год»
- Длина: **120–180 симв.** — одно законченное предложение легче цитировать, чем многострочный блок

✅ Правильно: «Смартфоны Xiaomi в GOODMi — гарантия 1 год, доставка СДЭК, самовывоз в 6 точках Крыма, с 2016 года.»
❌ Неправильно: «GOODMi — фирменный магазин Xiaomi в Крыму. Здесь вы найдёте широкий выбор смартфонов.»

**`LocalBusiness.description`** — 2–3 предложения: специализация + гео + главный USP. Не повторять `WebPage.description` дословно.

Пример: «GOODMi — фирменный магазин техники Xiaomi в Крыму с 2016 года. Самовывоз в 6 точках: Севастополь, Симферополь, Ялта. Доставка СДЭК по всей России, трейд-ин, покупка в кредит.»

**[v2] `LocalBusiness.sameAs` — обязательно:**

```json
"sameAs": [
  "https://yandex.ru/maps/org/goodmi/81345582117/"
]
```

Зачем: Яндекс Нейро и ChatGPT Search используют `sameAs` для подтверждения авторитетности организации. Ссылка на верифицированную карточку Яндекс Карт — прямой сигнал доверия.

### Step 3a — Примеры эталонного вывода

Использовать как ориентир формата и длины, не как источник готовых слов. Title-варианты и H1 в примерах — конкретные (демонстрируют оси и расчёт длины); description намеренно дан в виде **скелета** — с плейсхолдерами вместо конкретных USP/характеристик. Причина: пять полностью «мясных» примеров с одинаковым набором USP раньше перевешивали правило (демонд-фильтр) и копировались как есть, вместо пересчёта из реальных данных Step 2b для конкретной страницы — см. разбор в [[project-seo-meta-builder-v2-refinement]]. Заполнять плейсхолдеры — только по «Главному принципу композиции» и «Демонд-фильтру USP» выше, данными конкретной страницы.

#### Пример 1: Топовая категория — «Смартфоны Xiaomi»

```
H1: Смартфоны Xiaomi   (16 симв.)
```

**Таблица покрытия ключей (с флагами):** строки — по убыванию «Балл / вес». Именно этот порядок определяет, в какой последовательности ключи попадают в гибкие слоты title/description (см. «Главный принцип композиции» в Step 3) — не пересортировывать при заполнении тегов.

> Колонка «Балл / вес»: для ключей из Wordstat-кластера (Step 2b, основной метод) — взвешенный балл по гео-каскаду (топ-1 / топ LSI / хвост, не число 0–100). Для ключей из SERP-эвристики или внешних keyword data (fallback) — «Эффективный вес» по шкале ≥35 / 15–34 / <15. Не смешивать две шкалы в одной строке — указывать метод в скобках, если оба использовались на одной странице.

**[v2] USP-фильтр (обязательно для товарных страниц — категория / серия / модель / аксессуары):**

Материализовать решение по каждой USP-фразе из «Approved USPs», а не держать его в уме — иначе демонд-фильтр молча не срабатывает.

```

|---|---|---|
| гарантия 1 год | не проверяется | ✅ разрешённое исключение (макс. 1 без подтверждения) |

| самовывоз | N | ✅ / ❌ |
| трейд-ин | N | ✅ / ❌ |
```

Правило: не более одной строки со статусом «✅ разрешённое исключение» без подтверждения в LSI. Остальные ✅ — только если сама фраза реально встретилась в Step 2b/associations для этой страницы.
